# One Piece lifecycle inventory

The harness has three places where state matters. Agents and tools construct domain records. The scheduler and engine hold resources across asynchronous work. Recovery and the dashboard reconstruct state from evidence written by another process. A valid record shape, a legal transition, and proof that an external operation actually occurred are different guarantees.

## Domain records

| Machine | State and evidence | Owner |
| --- | --- | --- |
| Run and shutdown | A running run can enter a terminal status and drain outstanding reviews. Draining is only valid after research has stopped. The dashboard derives interrupted status by probing the owner lock. | `core/src/types.ts`, `engine/src/harness.ts`, `dashboard/src/index.ts` |
| Node and assignment | Pending, running and parked nodes can settle as done, cut, merged, archived or failed. Terminal nodes ignore stale wakeups. A research peer that returned its assignment transitions directly to compatible open work or an independent follow-up. Recovery accepts legacy parked records. Reassignment clears its completion and checkpoint together. | `core/src/tree.ts`, `engine/src/peer-work.ts` |
| Agent identity and completion | Claims reviewers need an author and a finding. Hidden and root reviewers need a target. An independent finding check is a swarm peer tied to an author and revision. Only a leaf can own a job handoff, and the handoff selects at least one output when the leaf is created. Merge metadata belongs to merged nodes. A completion kind carries a human-readable summary. Historical summaries acquire a kind when read. | `core/src/types.ts`, `store/src/documents.ts` |
| Findings and verification | New and revised submissions enter the review queue. A deferred review carries its error and retry time. A decision carries a nonempty history ending in that verdict. Organization belongs to reviewed findings. A submission carries a frozen digest, a receipt-based fallback note, or neither. A verifier pin requires a scope. Running a checker against a frozen revision requires both scope and digest. The writer rechecks the revision after awaiting the reviewer. | `engine/src/trust.ts`, `engine/src/verification.ts` |
| Questions | Tree runs route questions between agents, with a deadline and a logged default. A defaulted question can still receive a late answer. The stored escalation state is historical. Peer environments use the task and review boards. | `module-questions/src/index.ts` |
| Tasks and messages | Claim consumes open work. Release consumes a side claim. A private assignment settles with its owner and can then be retried. Blocked and interrupted tasks retain a result. Direct messages require a recipient. A reply belongs to a handled operator message. Delivery is a separate state for broadcasts. | `engine/src/task-transitions.ts`, `engine/src/environment.ts`, `engine/src/peer-work.ts` |
| External controller | Pending commands may settle once as applied or failed, each with a result. Only the operator can originate a control record. Targeted commands name an assignment. A complete close cites at least one finding. SQLite validates action payloads before dispatch and the dispatcher checks current ownership and accepted verdicts. | `core/src/swarm-command.ts`, `engine/src/environment.ts`, `store/src/documents.ts` |
| Board threads | Opening posts have no reply pointers. Replies identify both the topic and immediate parent. Run and audience membership are checked when resolving the parent. | `module-board/src/index.ts` |
| Recommendations | Open recommendations can be applied or dismissed. An identical replay is idempotent. A conflicting second resolution fails. | `engine/src/tree-tools.ts` |
| Epochs | A reviewer chooses continue, conclude or start. Only a start decision with a handoff reaches epoch creation. A successor number is a validated integer greater than one. A successor carries a trigger, mode and handoff. A fresh decision or epoch carries no branches. Budget, live descendants and user authority are checked against current evidence. | `engine/src/oversight.ts` |
| Job and output receipts | A gated job owns its preflight command. Transition functions consume the specific source state. Voluntary withdrawal consumes a pending job and cannot carry execution fields. Success requires admission, both timestamps and exit zero. An execution failure has a start time. Gate and admission failures cannot claim one. A cached result originates from a success. A required-output spec names at least one file. A missing output cannot carry a verified digest. Admission owns the pre-run output baseline. Required files must all have verified fingerprints. A recovered compiler-smoke attempt needs its saved toolchain. | `scheduler/src/index.ts`, `scheduler/src/job-transitions.ts`, `scheduler/src/output-files.ts` |
| Evaluation | Grading consumes a terminal run receipt. Only a stopped evaluation can carry a timeout flag. Health is derived from accumulated issues. A verified best result requires a submitted frozen revision and a passing held-out grade. Raw workspace scores are also recorded. | `evals/src/index.ts` |

## Resource ownership and asynchronous state

| Machine | Representation and runtime boundary |
| --- | --- |
| Pool and host lease | A pool holds either a set of shared job IDs or one exclusive job ID. GPU-enabled command options require a launcher, readiness timeout and admission callback. The ready byte, host inventory and lease ownership are runtime observations. |
| Sandbox command | Admitting and executing own a deadline and start time. Stopping retains one reason and clears the deadline. Closed commands own neither a deadline nor an admission callback. The execution clock starts after the readiness callback. Descriptor closure and host signals still require runtime handling. |
| Agent slots and provider quota | Acquisition moves one permit through queued, preparing and held phases. Only a held permit can be released. Acquisition returns an idempotent release capability. The slot state distinguishes free, held and parked, with overlapping waits tracked on the parked variant. Provider RPM also depends on a shared time window and a file lock. |
| Budget and report reserve | The reporting phase advances from working to reserve, exhausted or finalized. The tree records child allocation, one-time refunds and late charges. Numerical conservation and overrun detection require actual usage values. |
| Watchdogs and consultations | Population monitoring distinguishes observation, warning and recovery. The work watchdog tracks the first check, second check and release check. Only the latter two retain the previous warning's call count. Replay checks warning order and the count for that evidence window. A legacy epoch consultation progresses from preparation to awaiting a reviewer, then resolves one decision. Only the awaiting phase owns a reply capability. |
| Review ownership and recovery | Initializing, active, draining and finalizing each own the SQLite writer lock. Only active ownership carries the polling timer. Finalizing and closed reject late provider accounting. Outstanding reviews are keyed by finding and revision. Scheduler and filesystem tests exercise durable recovery. |
| Beam launch and staging | Prepared and acknowledged launch identities describe the persisted provider receipt. The launch owns either a startup-marker deadline with a partial line or an application deadline. Staging projects readiness from its terminal volume disposition. Provider identity, markers, prefixes and hashes require validation against external evidence. |
| Peer terminal and tool catalog | The terminal decodes its tool arguments into shell or script mode. Only shell mode owns shell capabilities and slot-yield options. A peer replaces its available commands and their versioned catalog view together. A script accepts calls, drains admitted calls, then closes. Only the accepting phase owns the queue and sequencing barrier. Tool execution still validates availability and the assignment lifetime. |
| Transcript compaction | The recent tail starts empty, retains the newest turn, and then begins archiving when it reaches the size threshold. Once archiving starts, older turns stay in the archive, with pinned messages retained separately. |
| Dashboard | The live feed has idle, loading and streaming states. Only the streaming variant owns an EventSource. Board pages carry a request identity and an explicit loading, ready or error result. Task-board messages can carry a prior assignment or job listing for return navigation. Only the jobs listing owns pool and task filters. The annotated browser machines are compiled by the normal typecheck. |
| Modules, skills, credentials and context | Module activation already uses off, deferred and active. Loaded groups, assigned skills, grants, artifact reads and provider registrations use membership in sets or maps. Credential refresh and durable artifact publication also depend on locks and I/O. |

## Shared state and its owners

| Previously shared | Owner and access |
| --- | --- |
| Free slot counters and waiter arrays in the engine and router | A permit actor per capacity limit accepts acquire, release, cancellation and pacing replies. Each caller receives a release handle scoped to one grant. Only the receiver mutates reservations. Slow provider pacing runs outside the mailbox. |
| Scheduler pool occupancy and spend across dispatch and completion callbacks | A scheduler mailbox grants shared or exclusive slots and receives workload completions by job ID. Submitted specs, public job receipts and pool configurations cross the caller boundary as snapshots. The host launcher still coordinates the physical resource. |
| Recursive event delivery and mutable event payloads | One FIFO receiver delivers persisted events in sequence. A listener may publish a follow-up while handling an event. Listeners and store readers receive isolated values. |
| Peer inbox buffers and arrays of notification callbacks | Each peer owns a single-reader inbox across assignments. Waiting readers share a one-shot arrival notification. Turn completion uses a separate broadcast signal. |
| Process-global reviewer decision map | Each consultation creates a one-shot reply addressed to its reviewer. Closing the consultation invalidates its sender. |
| Durable or cross-process state | SQLite transactions, the run-owner lock, the host lease, the Beam volume lock, and the router’s credential and request-window file locks span independent processes. An in-memory receiver alone cannot arbitrate those writers after a crash. |

The TypeScript mailbox drains synchronous messages on the Node event loop. Reentrant sends join the current queue. Long-running work sends its result back in a separate turn. This applies the single-owner and reply-channel pattern in Tokio to the existing runtime. Sends can wait behind earlier work, so the mailbox makes no formal lock-free progress guarantee.

## Enforcement and verification

The collection-to-document map governs both stores and the event bus. The collection determines what callers can write and what readers receive. Built-in lifecycle notifications have typed payloads. Extension events can still carry module-defined data. SQLite performs targeted lifecycle checks and compatibility upgrades on decoded copies. The compiler rejection fixtures cover impossible records and transitions, including closing without a finding, releasing a private assignment, adding handoff identity after creation, and mixing terminal modes. The raw records remain available for investigation.

Run `npm run typecheck` for the TypeScript packages, compiler rejection tests, and annotated dashboard scripts. Run `npm test` for integration coverage, including simulated agents, process death, leases, stale events and SQLite recovery. Use `python3 -m unittest discover -s tools/beam-job-check` and `python3 -m unittest discover -s tools/inkling-beam-stage` for the Beam fixtures. The Beam state modules can also be checked with `mypy --check-untyped-defs --ignore-missing-imports --follow-imports=silent tools/beam-job-check/tracked_pod.py tools/inkling-beam-stage/{stage_state,run,guest}.py`.

The inventory covers the first-party harness, its dashboard and its Beam staging controller. Provider implementations in vendored Pi, task-specific grader internals, arbitrary module events, and unannotated browser rendering code have separate verification boundaries. Static checks cannot establish liveness, fairness, concurrent ownership on another host or the authenticity of external evidence.
